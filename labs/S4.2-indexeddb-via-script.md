# Lab S4.2 — Ler IndexedDB por script

### Semana 4 (Aula 4 — "O que sobrou?") · ~25 min · Micro-lab de leitura assíncrona

> **Escopo.** Exclusivamente no jogo da memória. Os scripts **leem** o estado do seu próprio
> navegador; nada é enviado para fora.

---

## Objetivo

Treinar **uma única habilidade**: abrir uma base **IndexedDB**, listar seus *object stores* e ler
registros — via console assíncrono. É onde o histórico de partidas do jogo da memória realmente
mora, e o armazenamento que mais surpreende quem acha que "o navegador guarda no máximo cookies".

Você também exercita, de propósito, código **assíncrono** (`Promise`/`await`) — porque IndexedDB é
uma API baseada em eventos, e ler dela sem se atrapalhar com o assincronismo é a metade difícil.

---

## Pré-requisitos

- **S1.2** e **S4.1** concluídos.
- Seção sobre IndexedDB do material [Anatomia do Navegador](../docs/anatomia-do-navegador.md).

---

## Setup

1. Jogo da memória, login feito como Ana, com ao menos **uma partida concluída** (jogue até o fim — o resultado
   é enviado automaticamente — e clique em **Meu histórico** antes de começar, se ainda não tiver
   feito; é ao abrir o histórico que o IndexedDB é preenchido).
2. DevTools → Console.
3. Confirme visualmente na aba **Application → IndexedDB** que existe ao menos uma base; anote o
   nome e o nome de um *object store*.

---

## Roteiro

Execute no console, um passo por vez. O DevTools aceita `await` no topo, o que facilita.

1. **Listar bases:**
   ```js
   await indexedDB.databases()
   ```

2. **Abrir uma base** e inspecionar seus object stores. Ajuste `NOME_DA_BASE`:
   ```js
   const db = await new Promise((resolve, reject) => {
     const req = indexedDB.open('NOME_DA_BASE');
     req.onsuccess = () => resolve(req.result);
     req.onerror = () => reject(req.error);
   });
   Array.from(db.objectStoreNames);   // lista os object stores
   ```

3. **Ler todos os registros** de um object store. Ajuste `NOME_DO_STORE`:
   ```js
   const registros = await new Promise((resolve, reject) => {
     const tx = db.transaction('NOME_DO_STORE', 'readonly');
     const store = tx.objectStore('NOME_DO_STORE');
     const req = store.getAll();
     req.onsuccess = () => resolve(req.result);
     req.onerror = () => reject(req.error);
   });
   console.log(registros.length, 'registros');
   registros
   ```

4. Localize o registro da partida que você acabou de salvar. Ele identifica o **jogador**
   (Ana) de alguma forma? Esse vínculo fica explícito no registro?

5. Acrescente à sua tabela de inventário (S1.2) a linha do IndexedDB, agora com conteúdo real.

---

## Perguntas-guia

1. Quantos object stores a base tinha? O que cada um parece guardar?
2. O conteúdo do IndexedDB é **enviado ao servidor** automaticamente, como um cookie? Como você
   confirmaria isso? (Dica: só o Burp confirma se um valor local vira requisição — é exatamente o
   que o S5.1 vai provar.)
3. Um XSS conseguiria ler este IndexedDB? Por quê?
4. O registro da partida identifica o jogador de forma explícita? Guarde essa observação — é o ponto
   de partida do **S4.4**.

---

## Critérios de verificação

Você fez certo se:

- Listou os object stores e leu ao menos um conjunto de registros com sucesso.
- Localizou o registro da sua própria partida salva.
- Consegue explicar por que IndexedDB é acessível ao JS e, portanto, exfiltrável por XSS como o
  localStorage.

---

## Fronteira ética neste lab

- **Legítimo:** ler o IndexedDB do **seu** navegador em alvo autorizado; pedir à IA que **explique** a
  API de IndexedDB ou **ajude a corrigir** seu código assíncrono de leitura.
- **Vedado:** qualquer código que **envie** o conteúdo para fora, ou que leia armazenamento de outra
  origem. Leitura local para inventário é o escopo; exfiltração não é.
