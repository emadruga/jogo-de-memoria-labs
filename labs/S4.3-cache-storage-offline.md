# Lab S4.3 — Cache Storage e modo offline

### Semana 4 (Aula 4 — "O que sobrou?") · ~25 min · Micro-lab de observação sem rede

> **Escopo.** Exclusivamente no jogo da memória, ambiente local e autorizado.

---

## Objetivo

Treinar **uma única habilidade**: inspecionar o **Cache Storage**, ativar o modo offline do jogo, e
distinguir com precisão três mecanismos que se parecem mas não são o mesmo: **Cache HTTP** (S1.3),
**Cache Storage**, e **IndexedDB** (S4.2). É a lacuna mais evidente que faltava na sequência antes
deste redesenho.

A ideia central da Aula 4: a Cache API está disponível **na própria página**, sem exigir um service
worker — o service worker é o que permite **interceptar requisições** para responder mesmo sem rede.

---

## Pré-requisitos

- **S1.3** e **S4.2** concluídos.
- Referências [MDN — HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)
  e [MDN — CacheStorage.open](https://developer.mozilla.org/en-US/docs/Web/API/CacheStorage/open).

---

## Setup

1. Jogo da memória, com o **modo de treino offline** ativado ao menos uma vez (para popular o cache).
2. DevTools → **Application → Cache Storage** e **Network** abertos.

---

## Roteiro

### Parte 1 — o que está no Cache Storage

1. Em **Application → Cache Storage**, liste os caches existentes e, dentro de cada um, os recursos
   armazenados (URLs).
2. Compare essa lista com os recursos que você mediu no **S1.3** (Cache HTTP). São os mesmos
   recursos, mecanismos diferentes, ou conjuntos parcialmente sobrepostos?

### Parte 2 — acessar a Cache API sem sair da página

3. No console, sem envolver nenhum service worker, execute:
   ```js
   const nomes = await caches.keys();
   nomes
   ```
   Isso prova que a Cache API é acessível **diretamente pela página** — não exige um service worker
   para ser **lida**.

### Parte 3 — modo offline de verdade

4. Em **Network**, marque **Offline** (ou desligue a rede do sistema, conforme orientação do
   docente).
5. Recarregue a página. O que continua funcionando? A página e o tabuleiro de cartas aparecem? O
   estilo (CSS) carrega? O login funciona? O que acontece ao abrir o **Ranking**?
6. Tente **concluir uma partida** enquanto offline (o resultado é enviado automaticamente ao
   terminar). O que acontece?
7. Volte a ficar **online** e repita o teste de enviar o resultado.

---

## Desafio

Depois do teste offline: os dados do IndexedDB (S4.2), que você ainda consegue ler pelo console sem
rede, e os recursos do modo de treino (Cache Storage), servidos pelo service worker, continuaram
disponíveis pelo **mesmo** motivo? O botão **Meu histórico** mostrou esses dados offline? Explique,
nomeando os dois mecanismos separadamente.

---

## Perguntas-guia

1. O Cache Storage e o Cache HTTP guardam os **mesmos** recursos, neste jogo? Se não, por quê?
2. Foi preciso um service worker **ativo e controlando a página** para o modo offline funcionar? Como
   você confirmaria isso em **Application → Service Workers**?
3. O **envio do resultado** da partida funcionou offline? Se não, o que isso revela sobre a diferença entre "ler
   conteúdo cacheado" e "persistir um resultado que precisa do servidor"?
4. Recursos **privados** de conta (ex.: seu histórico pessoal) deveriam entrar no cache de treino
   offline, que é público? Por quê?

---

## Critérios de verificação

Você fez certo se:

- Lista os caches e recursos do Cache Storage e os distingue, com evidência, do Cache HTTP (S1.3).
- Testou o modo offline de verdade (rede desligada) e registrou o que funcionou e o que não
  funcionou.
- Articula a diferença entre Cache Storage (conteúdo servido offline) e IndexedDB (dados
  estruturados da aplicação) sem confundir os dois.

---

## Fronteira ética neste lab

- **Legítimo:** inspecionar o Cache Storage do **seu** navegador; testar o modo offline preparado
  para o laboratório; pedir à IA que **explique** a relação entre Cache API e service worker.
- **Vedado:** nada ofensivo neste lab — é observação de um recurso legítimo da aplicação.

---

## Fechamento defensivo

Anote: recursos de **treino offline** devem ser explicitamente públicos e identificados como tal na
interface; dados privados de conta **não** devem ser pré-cacheados para uso offline sem controle de
acesso equivalente ao que existe online.
